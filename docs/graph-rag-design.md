# 그래프 RAG 도입 설계

> 기존 검색(벡터 RAG) 위에 **그래프 RAG**를 얹어, 여러 정보를 연결해야 답이 나오는 질문의 품질을 높이는 설계.
> 개념 설명(1~4, 6~7절)과 아키텍처 구조(5절, 부록)를 함께 담았다.

---

## 한 줄 요약

지금의 **벡터 RAG**(의미가 비슷한 문장을 찾아 답하는 방식)는 단순 조회엔 강하지만 **"여러 정보를 연결해야 답이 나오는 질문"에는 약하다.** 문서 속 개념들을 **그래프(연결 지도)** 로 만들어 두는 **그래프 RAG**를 얹으면 이런 질문의 답 품질이 좋아진다.

---

## 1. 무엇이 문제인가

### 지금의 벡터 RAG가 하는 일

사용자가 질문하면 시스템은 질문을 **임베딩**(의미를 숫자 벡터로 변환)해 **의미가 비슷한 문장(청크)** 을 벡터 검색으로 찾고, 그걸 근거로 답을 만든다. "환불 기간이 며칠인가요?" 같은 **단순 조회**에는 잘 맞는다. 답이 한 청크 안에 다 들어 있기 때문이다.

### 못 하는 것

**여러 정보를 이어 붙여야 답이 나오는 질문**이 약하다.

> 예: **"A회사 환불정책이랑 B회사 정책 중 어디가 더 유리해?"**

이 답을 만들려면 (1) A회사 정책을 찾고 → (2) B회사 정책을 찾고 → (3) 둘을 비교해야 한다. 이 세 정보는 보통 **서로 다른 청크에 흩어져** 있어서, 벡터 검색(비슷한 문장 찾기)만으로는 조각들을 **연결**하지 못한다.

이렇게 **여러 단계를 거쳐야 답이 나오는 질문**을 이 문서에서 **"연결형 질문"** 이라 부른다.

---

## 2. 그래프 RAG란 무엇인가

**그래프**는 쉽게 말해 **관계도**다. 인물 관계도나 지하철 노선도를 떠올리면 된다.

- **점(개념)**: A회사, 환불정책, 예외조항 …
- **선(관계)**: "A회사 **─가지고 있다→** 환불정책", "환불정책 **─예외→** 디지털 상품"

벡터 RAG가 **"비슷한 문장을 찾아오는 사서"** 라면, 그래프 RAG는 여기에 **"개념들이 어떻게 연결돼 있는지 아는 지도"** 를 하나 더 얹는 것이다.

> 벡터 RAG를 **버리는 게 아니라 위에 하나 더 얹는다.** 둘(벡터+그래프)을 같이 써서 서로의 약점을 메운다.

연결형 질문이 들어오면, 이 그래프를 따라 **"A회사 → 환불정책 → 예외조항"** 처럼 관계를 타고 가서 흩어진 청크를 모아 온다.

---

## 3. 도입하면 좋아지는 점

### (1) 연결형 질문의 답 품질 향상 — 주 목표

비교 질문, 조건이 얽힌 질문("A회사 정책의 예외는 뭐고, 그게 언제 적용돼?")의 답이 더 정확하고 빠짐없이 나온다.

### (2) 대화가 이어질수록 더 빠르고 저렴해진다

한 대화에서 등장한 개념을 시스템이 **기억**해 둔다. 대화가 이어질수록 매번 처음부터 다 뒤질 필요가 없어진다.

| 턴 | 질문 | 시스템이 하는 일 | 결과 |
|---|---|---|---|
| 1 | "A회사 환불정책이랑 B회사 비교해줘" | 전체를 다 찾고 관계도까지 탐색 (제일 무거움) | 좋은 모델로 꼼꼼히 |
| 2 | "A회사 예외 조건은?" | 1턴에서 "A회사"를 기억 → 그 부분만 짚어봄 | 더 가볍고 빠르게 |
| 3 | "방금 말한 내용 요약해줘" | 새로 찾을 게 없음 → 앞 대화만 정리 | 가장 가볍게 |

즉 **뒤로 갈수록 일이 줄어드는 구조**라 응답이 빨라지고 비용도 내려간다.

### (3) 두 종류의 세션 기억 — langchain vs graph_context

위 "기억"은 사실 **성격이 다른 두 저장소**로 나뉜다. 둘 다 문서 본문을 저장하는 게 아니라(본문은 MinIO·Qdrant·PostgreSQL에 있음), **대화 세션 동안의 작업 기억**을 저장하되 그 종류가 다르다.

| | langchain Redis | RAG Redis (`graph_context`) |
|---|---|---|
| 소유 | langchain-service | rag-storage-service |
| 키 | `session:{id}:messages`, `:questions` | `rag:session:{id}:graph_context`, `graph:query:{hash}`, `entity:link:{term}` |
| 저장 내용 | **실제 오간 대화 원문**(사람·AI 메시지 텍스트) | **검색용 구조화 문맥**(활성 엔티티, resolve된 개념, 검색 결과 캐시) |
| 답하는 질문 | "무슨 **말**을 했는가" | "무슨 **개념**을 검색했고 지금 뭐가 활성인가" |
| 목적 | 대화 연속성(요약·맥락의 원문 재료) | 검색 연속성(다음 검색을 더 싸고 정확하게) |
| 원본/캐시 | 대화의 **원본**(source of truth) | **캐시** — 미스 시 전체 재검색 폴백 |

위 3턴 예시에 대입하면:
- **langchain messages** = "무슨 말을 했나" → 3턴 "요약해줘"의 실제 **원문 재료**.
- **graph_context** = "무슨 걸 검색했나" → 2턴에서 "A회사"가 이미 resolve됐음을 알아 1-hop만, 3턴은 "검색 불필요(CACHE_HIT)" 판단.

그래서 소유도 나뉜다. `graph_context`는 검색 도메인 데이터라 **RAG가 소유**하고 langchain은 대화 메모리만 가진다. 둘은 `sessionId`만 공유하고 데이터를 왕복시키지 않는다(모듈 경계).

## 4. 어떻게 만드나 — 큰 그림

크게 **두 순간**으로 나뉜다: **① 문서를 넣을 때**, **② 질문을 받을 때**.

### ① 문서를 넣을 때 — Pass1로 정리 후 청킹, Pass2로 관계 추출

핵심은 **청킹을 하기 전에 Pass1을 먼저** 돌리는 것이다. 순서는 다음과 같다.

```
PARSE → CLEAN → [Pass1] → CHUNK → EMBED → UPSERT → [Pass2]
```

- **Pass 1 — 청킹 전 (LLM 한 번 호출)**
  파싱·클리닝까지 끝난 **문서 전체**를 LLM에 한 번 넣고, 한 번의 호출로 **두 가지**를 돌려받는다.
  1. **canonical 엔티티 사전** — 문서에 나오는 개념 목록. "환불정책"과 "환불 정책"처럼 같은 개체를 다르게 쓴 표현을 하나로 통일(엔티티 레졸루션)해 문서 단위로 확정.
  2. **정리본** — 그 엔티티를 기준으로 **문서 자체를 재정리한 버전**. 흩어진 같은 주제를 모으고 표현을 정돈한 문서.

- **CHUNK·EMBED·UPSERT — 정리본 기준으로**
  이후 청킹은 원본이 아니라 **정리본**을 나눈다. 그래서 청크 경계가 좋아지고, 흩어졌던 같은 주제가 한 청크로 모여 **벡터 검색 recall도 함께 올라간다**(그래프뿐 아니라 벡터 RAG도 개선).

- **Pass 2 — UPSERT 후 (배치)**
  정리본 기반 청크를 대상으로 **관계(연결 고리)를 추출**한다. Pass1의 엔티티 사전을 컨텍스트로 주입해, 엔티티는 Pass1이 확정한 id로 링크한다.

> **왜 Pass1을 앞으로 빼고, 왜 두 번 하나?**
> 청크별로만 추출하면 **청크를 넘나드는 관계가 끊기고**(앞 청크 "A회사"와 뒤 청크 "환불정책 세부"의 연결 소실) 같은 엔티티가 **파편화**된다. 그렇다고 문서를 **통째로 한 번에** 관계까지 뽑으면 긴 문서 한계(컨텍스트 윈도우 초과, 중간 내용 놓침, 비용 급증)가 있다.
> Pass1을 청킹 앞에 두면 **전역 엔티티 사전 + 정리본**을 먼저 확보해, 그 정리본이 청킹·임베딩·관계 추출 모두의 품질을 끌어올린다. 즉 그래프만이 아니라 **벡터 RAG까지 같이 개선**되는 게 이 순서의 핵심 이점이다.

### ② 질문을 받을 때 — 벡터 검색과 그래프 탐색을 합친다

1. **벡터 검색** (기존) — 질문과 의미가 비슷한 청크를 찾음
2. **그래프 탐색** (신규) — 질문 속 엔티티를 그래프에서 찾아 관계를 타고 관련 청크를 모음

두 결과를 **fusion(융합)해** 가장 관련 높은 근거(citation)를 골라 답을 만든다.

> 안전장치: 그래프 탐색이 실패하거나 느리면 **기존 벡터 검색만으로도 정상 동작**한다. 그래프는 품질을 더하는 **보강재**이지 필수 부품이 아니다.

## 5. 아키텍처 구조

### 5.1 질문 처리(런타임 QA) 흐름

각 저장소는 소유 서비스가 단독 관리하고, 두 서비스(rag-storage / langchain)는 **`sessionId`만 공유**한다.

**저장소 소유권** — `graph_context`(그래프 세션 문맥)는 **rag-storage 소유**. 검색 도메인 데이터라 RAG가 생산·소비하고 langchain은 관여하지 않는다(모듈 경계). graph_context는 원본이 아닌 **캐시**로 취급(세션 24h 미러, 미스 시 전체 재검색 폴백).

**폴백 원칙(모두 하위 호환)**: graph_context 미스→전체 재검색 / 그래프 탐색 타임아웃→벡터 단독 / 질문 프로파일 없음→기존 지연+비용 라우팅.

### 5.2 인덱싱 파이프라인 — Pass1(정리)·Pass2(관계) 삽입

Pass1은 **CLEAN과 CHUNK 사이**(엔티티 사전+정리본), Pass2는 **UPSERT 뒤**(관계 추출)에 삽입한다.

```
PARSE → CLEAN → EXTRACT_ENTITY(Pass1) → CHUNK → EMBED → UPSERT → EXTRACT_RELATION(Pass2)
```

```
[문서 업로드]  (PDF, Notion, Confluence, DB…)
      │
      ▼  비동기 파이프라인 (스테이지별 Worker · ~1s 폴링)
│ ┌─ PARSE·CLEAN ────────────── RagPccWorker (파싱·정제)
│ ▼
│ ┌─ EXTRACT_ENTITY [Pass1, 신규] ── RagGraphEntityWorker  (LLM 1콜)
│ │    입력: 파싱·클리닝된 문서 전체
│ │    반환: ① canonical 엔티티 사전   ② 엔티티 기준 정리본
│ │    엔티티 레졸루션 문서 단위 확정 → rag_entity 저장 + entity:link 선워밍
│ │    원본 → MinIO 저장
│ │    ※ Pass1 실패 시: 원본(클리닝본)으로 폴백 청킹 → 벡터 RAG 정상, 그래프만 degrade
│ ▼
│ ┌─ CHUNK ──────────────────── RagPccWorker
│ │    정리본을 청킹 → MinIO(chunk.txt) + PostgreSQL(rag_chunks)
│ ▼
│ ┌─ EMBED ──────────────────── RagEmbedWorker
│ │    rag_chunks 배치 임베딩 → rag_embedding_parts
│ ▼
│ ┌─ UPSERT ─────────────────── RagUpsertWorker
│ │    Qdrant 벡터+payload 적재  ── 여기서 벡터 검색 이미 가능 ──
│ ▼
│ ┌─ EXTRACT_RELATION [Pass2, 신규] ── RagGraphWorker  (청크 배치)
│ │    청크별 관계 추출 — Pass1의 엔티티 사전을 공유 컨텍스트로 주입
│ │    "…예외가…" → [e1]-(HAS)-[e2]-(EXCEPTION)-[e3] (엔티티는 Pass1 id로 링크)
│ │    ▼ 저장 (PostgreSQL 그래프)
│ │      rag_entity_relation ← Pass 2가 채움
│ │      rag_entity_chunk    ← 브리지 (그래프↔청크↔벡터 연결)
│ ▼
│ status=SUCCEEDED
```

**Pass1을 CHUNK 앞에 두는 이유**: 정리본이 청킹·임베딩·관계 추출 모두의 입력이 되므로, **그래프뿐 아니라 벡터 검색 recall까지 함께 개선**된다. 대신 Pass1(LLM)이 벡터 검색의 임계 경로에 들어오므로, **실패 시 원본 청킹으로 폴백**해 벡터 RAG 가용성을 지킨다.

**Pass1 모델 선택**: 정리본 품질이 전체 검색 품질을 좌우하므로 **문서 용량 기반으로 모델을 라우팅**한다 — 소형 문서는 경량 모델, 대형 문서는 고급 모델. (질문 시점 라우팅[8절]과 별개인 **인덱싱 시점 라우팅**.)

**Pass2를 UPSERT 뒤에 두는 이유**: chunk_id·본문 확정 후라야 브리지가 안전하게 청크를 참조하고, 관계 추출이 실패해도 벡터 RAG는 이미 정상 동작(그래프만 재시도).

**인덱싱↔검색 접점**: `rag_entity_chunk`(브리지) + `entity:link` 캐시. 그래프 탐색으로 도달한 "개념"을 브리지가 실제 청크(citation) 텍스트로 환원해야 LLM이 읽을 수 있다. **인덱싱의 엔티티 추출과 검색의 엔티티 링킹이 같은 `entity:link` 캐시·정규화 규칙을 공유**해야 함(Pass1이 사전을 확정해 이를 구조적으로 보장).

### 5.3 그래프 어휘(vocabulary) 정의 방식 = 하이브리드

| 층위 | 주체 | 담당 |
|---|---|---|
| 사전 정의(틀) | admin | Entity TYPE 10~20개, RELATION 6~10개(더 타이트), (선택) 카테고리별 세트 |
| 추출(인스턴스) | LLM | **Pass1**: canonical 엔티티 사전 + 정리본(엔티티 기준 재정리 문서) / **Pass2**: 청크별 관계(`relation_label` 원문·`confidence`) |
| 후처리(정규화) | 시스템 | 동의어 정규화·타입 매핑(entity resolution) → **Pass1에서 문서 단위 확정** |

- **저장소**: TYPE/RELATION 닫힌 세트는 Java enum이 아니라 **DB `rag_graph_vocab_entry`**(kind=`TYPE`|`RELATION`, builtin seed + admin CRUD·활성/soft-delete). 그래프 인스턴스 테이블의 `type`/`relation` 컬럼은 `varchar`로 그 이름을 저장한다.
- **RELATION을 TYPE보다 조이는 이유**: TYPE이 늘어도 탐색 쿼리는 안 바뀌지만, RELATION이 늘면 탐색 경로 조합이 폭증하고 같은 개념이 여러 relation으로 흩어져 파편화됨. 세트 밖 관계는 `RELATED_TO` fallback으로 흡수.
- **초기 세트**: 추측이 아니라 샘플 20~50문서 open extraction → 빈도 집계 → admin 검수·동결 후 닫힌 세트 강제. (현재는 업로드 엔티티 검수로 builtin 9+9 확정, open extraction 빈도표 플로우는 후순위.)
- **[결정] 추출 프롬프트 = RAG 내부 소유**: Pass1(엔티티+정리본)·Pass2(관계) 추출 프롬프트는 **rag-storage가 직접 관리하는 내부 프롬프트**로 진행한다. admin이 정의하는 vocabulary(TYPE/RELATION 세트)는 이 프롬프트에 **주입되는 값**일 뿐, 프롬프트 본문 자체는 RAG 소유. (LLM 실행은 AI Gateway 경유하지만, 프롬프트 정의·버저닝은 RAG가 함 — langchain·게이트웨이가 관여하지 않음.)

## 6. 만들 때 신경 써야 할 점

| 항목 | 걱정 | 대응 |
|---|---|---|
| **citation 표기 수준** | 정리본은 LLM 재작성 텍스트라 청크가 원본과 다를 수 있음 | **[결정] 원본 텍스트는 별도 보관하지 않음.** citation은 **어느 문서 출처인지(document 수준)만** 밝히고, 원본 span 환원은 하지 않음 |
| **Pass1 가용성** | Pass1이 청킹 앞(임계 경로)에 있어 벡터 검색이 Pass1 성공에 종속 | Pass1 실패 시 **원본으로 폴백 청킹** → 벡터 RAG 정상, 그래프만 degrade |
| **비용 / Pass1 품질** | Pass1 정리본이 전체 검색 품질을 좌우하고, 정리본(문서 전체) 출력이라 토큰이 큼 | **[결정] 문서 용량 기반 모델 라우팅** — 소형 문서→경량 모델, 대형 문서→고급 모델. 품질이 중요한 Pass1엔 비용을 아끼지 않음 |
| **같은 개념 묶기** | "환불정책"≠"환불 정책"으로 취급하면 그래프 파편화 | Pass1에서 문서 단위 단일 사전으로 병합 일원화 |
| **검색 속도** | 벡터+그래프 병행 시 지연 증가 | 그래프 탐색 타임아웃(예: 300ms), 초과 시 벡터 단독 폴백 |
| **정확한 삭제** | 문서 삭제 시 그래프·캐시·정리본도 함께 삭제 | rag_entity_chunk·엔티티·graph:query/entity:link + 정리본 연쇄 삭제 |
| **저장소 선택** | 그래프 DB 초기 락인 회피 | 1~2 hop이면 관계형 인접 테이블+재귀 CTE로 시작, 병목 시 AGE 승격 |
| **보안** | 볼 수 있는 자료만 검색돼야 함 | 검색 전 구간 `userNo`·`categoryId` 스코프 강제 |

## 7. 진행 순서

품질 개선이 주 목표이므로 **그래프 구축부터 먼저** 한다.

| 단계 | 내용 | 기대 효과 |
|---|---|---|
| 0 | 연결형 질문 골든셋 20~50문항 구축 | 효과를 숫자로 측정할 기준 |
| 1 | EXTRACT_ENTITY(Pass1: 정리본)·EXTRACT_RELATION(Pass2) + 관계형 traverse + RRF fusion | 연결형 질문 품질 향상(핵심), 정리본으로 벡터 recall도 개선 |
| 2 | `graph:query:*` 결과 캐시 | 반복 질문 latency↓ |
| 3 | `rag:session:*:graph_context` | follow-up 문맥 유지 |
| 4 | 질문 프로파일 → AIG 라우팅 연동 | 질문 난이도 기반 모델 선택(비용↓) |

> 0단계(측정 기준)를 먼저 두는 이유: 기준이 없으면 "그래프를 넣어 좋아졌다"를 증명할 수 없다.

## 8. (후순위) 비용 최적화 — 질문 난이도에 맞는 모델 선택

품질이 아니라 **비용**을 위한 레이어로, 앞 단계 검증 후 얹는다. 라우팅 주체는 **AI Gateway의 `RouteSelectionService`**, RAG는 retrieve 직후 만든 **질문 프로파일**을 입력 신호로 넘길 뿐이다.

검색을 하다 보면 질문이 쉬운지 어려운지가 자연스럽게 드러난다(관련 개념 수, 관계를 몇 hop 탔는지, 근거 건수 등 — **어차피 계산되는 부산물**이라 별도 LLM 호출 없음).

- **쉬운 질문**(단순 조회, 캐시 히트) → 경량 모델
- **어려운 질문**(multi-hop 비교·추론) → 고급 모델

```
perfScore  = 지연·비용 기반 (기존)
fitScore   = 질문 프로파일 ↔ 모델 적합도 (신규)
finalScore = (1 - w) * perfScore + w * fitScore
```

질문 프로파일이 없으면 `fitScore`를 건너뛰고 기존 지연+비용 라우팅으로 폴백(하위 호환).

## 부록: 개발 세부 (확정·잔여)

- 스택: Spring Boot 3.4.2 / Java 17 / PostgreSQL(JPA) / Qdrant(WebClient) / MinIO. langchain-service는 FastAPI/Python 3.11 별도 모듈(Gateway 경유, RAG와 직접 통신 안 함).
- 삽입 지점: `RagJobStep`에 `EXTRACT_ENTITY`(Pass1)·`EXTRACT_RELATION`(Pass2) 2개 추가. 기존 `RagPccWorker`의 Parse·Clean·Chunk를 **PC(파싱·정제) / C(청킹)로 분리**하고 그 사이에 Pass1 삽입 → CLEAN success 대상을 `EXTRACT_ENTITY`로, Pass1 success를 `CHUNK`로, `UPSERT` success를 `EXTRACT_RELATION`으로 변경 → `ConsumerPipelineRunner.runOnce()` 연결.
- 정리본 저장: Pass1 산출 정리본을 MinIO에 저장(다음 CHUNK 입력). **원본은 별도 보관하지 않음** — citation은 document 수준 출처만 표기.
- Pass1 모델 라우팅: **문서 용량 기준**(소형→경량, 대형→고급). 인덱싱 시점 라우팅으로 8절 질문 시점 라우팅과 별개.
- 추출 프롬프트: Pass1·Pass2 프롬프트는 **RAG 내부 소유**(rag-storage에서 정의·버저닝). admin vocabulary는 주입 값일 뿐.
- **어휘**: Java enum → **`rag_graph_vocab_entry` DB**. 조회·CRUD API 완료. admin UI·open extraction 빈도표·entity resolution 정규화 일원화는 잔여.
