# 의미 청킹(Semantic Chunking) 도입 설계

> 지금의 고정 길이 청킹(글자 수 기준으로 자르기)을 **문장 간 의미 유사도가 끊기는 지점**을 경계로 삼는 방식으로 바꾸는 설계.

---

## 한 줄 요약

지금은 청크를 **글자 수(1200자)로 기계적으로 자른다.** 그래서 한 문단·한 주제가 청크 중간에서 잘리는 일이 흔하다. **인접 문장 간 의미 유사도가 뚝 떨어지는 지점**을 경계로 삼는 **의미 청킹**을 도입하면, 청크 하나가 한 주제를 온전히 담게 되어 벡터 검색과 답변 근거(citation)의 품질이 좋아진다.

---

## 1. 무엇이 문제인가

### 지금의 청킹

문서가 파싱·정제된 뒤, `langchain-service`의 PCC(Parse·Clean·Chunk)가 텍스트를 **글자 수 기준**으로 자른다.

- 최대 1200자(`max-chars`)가 되면 무조건 자름
- 잘린 경계에서 문맥이 끊기지 않게 120자(`overlap-chars`)를 앞뒤로 겹침
- 마지막 조각이 40자(`min-chars`) 미만이면 앞 청크에 붙임

### 못 하는 것

이 방식은 **글자 수만 볼 뿐 내용은 보지 않는다.** 그래서:

- 한 문단이 두 청크로 쪼개져 앞뒤 맥락이 끊긴다.
- 서로 다른 주제가 우연히 1200자 안에 같이 들어가면 한 청크에 섞인다.
- overlap(120자)이 어느 정도 완충하지만, "문장 중간"에서 자르는 문제 자체는 못 고친다.

결과적으로 벡터 검색이 "의미상 필요한 문장은 있는데 청크 경계 때문에 반쪽만 걸리거나, 상관없는 문장과 섞여 점수가 흐려지는" 문제를 겪는다.

---

## 2. 의미 청킹이란 무엇인가

핵심 아이디어는 단순하다: **문장을 하나씩 임베딩해서, 인접한 두 문장이 "의미적으로 이어지는지"를 유사도로 판단**하고, 유사도가 뚝 떨어지는 지점을 청크 경계로 삼는다.

```
문장1 ─유사도 0.89─ 문장2 ─유사도 0.91─ 문장3 ─유사도 0.31─ 문장4 ─유사도 0.85─ 문장5
                                        ▲
                                  여기가 주제 전환점 → 청크 경계
```

- 문장1~3: 유사도가 높게 유지됨 → 한 청크로 묶임
- 문장3→4: 유사도가 임계치 아래로 떨어짐 → 여기서 자름
- 문장4~5: 다시 높은 유사도 → 다음 청크로 묶임

즉 **"글자 수가 찼으니 자른다"가 아니라 "주제가 바뀌었으니 자른다."**

**경계 판단 방식 결정: 임베딩 유사도 breakpoint (LLM 미사용)**
문장마다 LLM에게 "여기서 끊을까요?"를 묻는 대신, 기존에 청크 임베딩용으로 쓰는 것과 별개로 **가벼운 임베딩 모델**로 문장 벡터만 뽑아 코사인 유사도를 계산한다. LLM 호출이 없어 비용이 낮고 결과가 결정적(deterministic)이다.

**임계치는 고정값이 아니라 percentile 기반**
문서마다 "문장 간 유사도의 평균 수준" 자체가 다르다(전문 문서는 전반적으로 유사도가 높고, 잡다한 문서는 낮음). 그래서 절대값(예: "0.5 밑이면 자른다")이 아니라, **그 문서 안에서 유사도 하위 N%(예: 하위 5%)에 해당하는 지점을 경계로 삼는 상대적 기준**을 쓴다. 문서 성격에 관계없이 안정적으로 동작한다.

## 3. 도입하면 좋아지는 점

### (1) 청크 하나가 한 주제를 온전히 담는다

주제가 바뀌는 지점에서 잘리므로, 벡터 검색이 찾아온 청크 안에 "질문에 필요한 문장 + 불필요한 다른 주제 문장"이 섞이는 일이 줄어든다.

### (2) citation 품질 향상

답변 근거로 보여주는 청크가 문맥적으로 완결된 단위가 되어, "왜 이 문장이 근거인지" 사람이 읽어도 납득이 간다.

### (3) 그래프 RAG의 Pass1(정리본)과 시너지

[graph-rag-design.md](graph-rag-design.md)에서 CHUNK는 원본이 아니라 Pass1이 만든 **정리본**(엔티티 기준으로 재정리된 문서)을 대상으로 한다. 정리본은 이미 같은 주제를 모아둔 상태라 의미 청킹의 경계 탐지가 더 깨끗하게 맞아떨어진다. 다만 **의미 청킹은 Graph RAG와 독립적으로도 가치가 있다** — Pass1 없이 원본 텍스트에 바로 적용해도 고정 길이 청킹보다 경계가 낫다.

## 4. 어떻게 만드나 — 파이프라인 반영

### 스테이지 구조는 그대로, 청킹 알고리즘만 교체

```
PARSE → CLEAN → (Pass1: EXTRACT_ENTITY, Graph RAG 도입 시) → CHUNK → EMBED → UPSERT → (Pass2, Graph RAG 도입 시)
                                                              ▲
                                                        여기만 바뀐다
```

**구현 위치 결정: `langchain-service`(PCC) 내부 확장**
청킹은 지금도 PCC가 실행하고 있고, RAG는 결과(청크 배열)만 받아 MinIO·PostgreSQL에 저장한다(`RagChunkWriter`). 이 경계를 그대로 유지한 채, **PCC 내부의 청킹 알고리즘만 고정 길이 → 의미 기반으로 교체**한다.

- rag-storage-service 쪽 계약(`PccChunkHints` 요청, `PccIngestResponse`의 `chunks[]` 응답 구조)은 그대로 유지된다.
- RAG는 여전히 `max-chars` / `overlap-chars` / `min-chars`를 PCC에 전달하지만, **값과 역할을 재정의**한다.

**주의 — 기존 1200자 값을 그대로 재사용하면 의미 청킹의 이점이 무력화된다.**
`max-chars=1200`은 고정 길이 알고리즘에서 "청크가 너무 커지지 않게" 튜닝된 값이다. 의미 청킹에서는 세그먼트 길이가 주제 크기에 따라 들쭉날쭉한 게 정상인데, 이 값을 그대로 하드 캡으로 두면 **딱 의미 청킹이 잘하는 일(긴 주제 하나를 온전히 묶는 것) 자체가 매번 다시 부서진다** — 즉 이점이 가장 큰 케이스에서 이점이 사라지는 역설이 생긴다. 그래서:

- **`max-chars` 상한을 크게 올린다**(예: 임베딩 모델의 입력 토큰 한도 근처까지). 이제 "품질을 위한 튜닝값"이 아니라 **"임베딩 모델이 아예 못 받는 극단적 케이스만 막는 기술적 방어선"**으로 역할을 바꾼다. 일상적으로 걸리는 값이면 안 되고, 정말 예외적인 긴 구간(예: 끊김 없이 이어지는 긴 인용문)에서만 개입해야 한다.
- **강제 개입이 필요해도 글자 수로 뭉텅 자르지 않는다.** 세그먼트가 새 상한을 넘으면, 먼저 그 구간 안에서 percentile 임계치를 더 낮춰(더 촘촘한 기준으로) **재귀적으로 재분할을 시도**한다. 그래도 자연스러운 경계를 못 찾을 때만(예: 유사도 변화가 거의 없는 단일 긴 문단) 최후 수단으로 글자 수 슬라이스 + overlap을 적용한다.
- `min-chars`도 재검토 대상이다. 아주 짧은 세그먼트를 무조건 인접 청크에 병합하면, 실제로는 독립된 짧은 주제(정의 한 줄, 표 캡션 등)를 억지로 섞어버릴 수 있다. 병합 여부를 정하기 전에 "다음 세그먼트와의 유사도"까지 참고하는 편이 안전하다(유사도가 높으면 병합, 낮으면 짧아도 유지).
- 의미 청킹 고유 파라미터(유사도 임계 percentile, 문장 묶음 단위 등)는 PCC 내부 튜닝값으로 두고, RAG-PCC 간 계약에는 노출하지 않는다.

### PCC 내부 청킹 흐름 (신규)

```
정제된 텍스트(원본 또는 Pass1 정리본)
      │
      ▼ 문장 분리 (한국어: 마침표만으로 부족 — 약어·번호매김·목록 고려)
[문장1, 문장2, 문장3, ... 문장n]
      │
      ▼ 문장별 임베딩 (경량 모델 — 청크 임베딩용 모델과 별개, 저비용 우선)
[v1, v2, v3, ... vn]
      │
      ▼ 인접 문장 코사인 유사도 계산
[sim(1,2), sim(2,3), ... sim(n-1,n)]
      │
      ▼ 유사도 하위 N-percentile 지점을 경계 후보로 표시
      │
      ▼ 경계 후보로 1차 세그먼트 분할
      │
      ▼ 세그먼트 > max-chars(상향 조정된 값)?
      │    ├─ Yes → 그 구간만 percentile을 낮춰 재귀적 재분할 시도
      │    │         └─ 그래도 실패 시에만 overlap-chars 겹치며 글자 수 강제 슬라이스(최후 수단)
      │    └─ No  → 유지
      │
      ▼ 세그먼트 < min-chars?
      │    └─ 다음 세그먼트와 유사도 확인 → 높으면 병합, 낮으면 짧아도 유지
      ▼
최종 chunks[] (기존과 동일한 응답 형태로 RAG에 반환)
```

## 5. 만들 때 신경 써야 할 점

| 항목 | 걱정 | 대응 |
|---|---|---|
| **안전장치 값 재사용의 역설** | 기존 `max-chars=1200`을 그대로 하드 캡으로 쓰면, 의미 청킹이 묶으려는 긴 주제일수록 매번 다시 강제로 잘려 이점이 무력화됨 | 상한을 임베딩 모델 토큰 한도 근처까지 크게 올리고, 초과 시에도 글자 수 슬라이스 전에 **재귀적 재분할**을 먼저 시도 |
| **비용/지연 증가** | 문장 단위 임베딩 호출이 청크 임베딩(EMBED 스테이지)과 별개로 추가됨 | PCC 내부에서 **경량/로컬 임베딩 모델** 사용(정확도보다 속도·비용 우선 — 경계 탐지용이지 검색용이 아님) |
| **한국어 문장 분리 정확도** | 마침표 기준 분리는 약어("Dr.", "1.2.3." 번호매김), 목록·표 항목에서 오분리 | PCC가 이미 담당하는 파싱 단계 지식(구조 정보)을 문장 분리기에 재사용 |
| **구조화된 구간(표·코드블록)** | 문장 임베딩 유사도가 무의미 | 이런 구간은 감지 시 의미 청킹을 건너뛰고 고정 길이 방식으로 폴백 |
| **문서가 매우 짧을 때** | 문장 수가 적으면(예: 3문장 이하) percentile 계산 자체가 불안정 | 문장 수 임계 미만이면 통짜로 한 청크 처리 |
| **기존 색인 문서** | 이미 색인된 문서는 알고리즘을 바꿔도 자동 적용 안 됨 | 재색인 필요 — 기존 재색인 스크립트(`scripts/reindex-graph-empty.ps1`) 계열로 배치 재처리 |
| **효과 측정** | "경계가 좋아졌다"는 주관적 — 숫자로 확인 필요 | 기존 골든셋(`docs/goldenset.json`, `scripts/golden-eval.sh`)으로 고정 길이 vs 의미 청킹 A/B 비교 |

### 5.1 안전장치 값 재사용의 역설 — 구체적 수치

한국어는 글자당 토큰 소모가 영어보다 적어서, 1200자는 대략 600~900 토큰 수준이다. 반면 임베딩 모델(OpenAI `text-embedding-3-*` 계열)의 입력 한도는 약 8191 토큰 — 글자 수로 환산하면 대략 6000자 이상까지 여유가 있다. 즉 지금의 1200자는 **모델이 못 받는 한계와 전혀 무관한, 순전히 "고정 길이 알고리즘 튜닝용" 숫자**였다.

- `max-chars`는 **4000~6000자 선**으로 올린다(정확한 값은 실제 사용 임베딩 모델의 토큰 한도 × 안전 마진으로 역산 — 6절 진행 순서의 튜닝 단계에서 확정).
- 재귀 재분할 알고리즘 예시: 초기 breakpoint 기준을 "유사도 하위 5%(percentile 95)"로 두고, 어떤 세그먼트가 새 `max-chars`를 넘으면 **그 세그먼트 내부만** 기준을 하위 10%, 15%로 단계적으로 완화하며 재귀 분할한다. 재귀 깊이를 2~3회로 제한해, 그래도 안 잘리면(예: 유사도가 끝까지 균일한 긴 인용문) 그때 글자 수 강제 슬라이스로 넘어간다. 이렇게 하면 "억지로 자를 때도" 가능한 한 의미 경계에 가까운 지점에서 잘리게 된다.

### 5.2 비용/지연 증가 — 어디서 얼마나 늘어나나

문서 한 건에 문장이 대략 200~400개 있다고 가정하면(10페이지 내외 문서 기준), 문장마다 임베딩 벡터가 필요하다. 이건 기존 `EMBED` 스테이지(청크 단위 임베딩, `AiEmbeddingClient` → AI Gateway 경유)와는 **별개의 추가 호출**이라, 그대로 API 임베딩을 쓰면 문서당 호출 수가 크게 늘고 비용·지연이 함께 증가한다.

- 그래서 PCC 내부에 **경량 로컬 임베딩 모델**(예: multilingual sentence-embedding 계열의 소형 모델)을 두고, 배치로 한 번에 처리하는 방식을 우선 검토한다. 로컬 모델은 정확도가 검색용 임베딩보다 다소 낮아도 무방하다 — 여기서는 "완전히 다른 두 문장인지"만 구분하면 충분하고, 검색 품질에 쓰이는 벡터가 아니기 때문이다.
- 로컬 모델을 쓰면 PCC 프로세스에 모델 파일을 번들링·버전 관리해야 하는 배포 부담이 새로 생긴다. 이 부담은 API 호출 비용·지연과 맞바꾸는 트레이드오프이므로, 프로토타입 단계(6절 1단계)에서 실측 비교가 필요하다.
- 지연 측면에서는, PCC가 이미 동기 처리하는 파싱·정제 단계에 문장 임베딩이 추가되므로 `CHUNK` 스테이지 처리 시간이 늘어난다. 대용량 문서는 워커 폴링 주기(~1s) 기준으로 여러 사이클에 걸쳐 처리될 수 있음을 감안해야 한다.

### 5.3 한국어 문장 분리 정확도 — 실패 사례와 대응

단순히 마침표(`.`)로 나누면 다음과 같은 경우 오분리가 난다.

- 약어·소수점: "2025. 11. 15." 같은 날짜, "1.2.3." 같은 번호매김이 문장 끝으로 오인됨
- 목록 항목: "① ~~~  ② ~~~" 처럼 문장부호 없이 이어지는 목록은 애초에 문장 경계 자체가 불명확
- 인용부호 안 마침표: 대화체 인용문 안의 마침표를 문장 끝으로 잘못 판단

`langchain-service`는 FastAPI/Python 기반이므로, 규칙 기반 정규식보다는 한국어 문장 분리 전용 라이브러리(예: `kss` 등)를 우선 검토한다. 또한 PCC가 파싱 단계에서 이미 확보한 레이아웃 정보(목록·표 셀 경계 등)를 문장 분리기에 넘겨, "이 줄바꿈은 레이아웃 때문이지 문장 끝이 아니다"를 구분하는 데 재사용한다.

### 5.4 구조화된 구간(표·코드블록) — 왜 유사도 판단이 무의미한가

표를 문장 단위로 쪼개면 "이름 | 나이 | 소속"처럼 의미상 연결되지 않는 짧은 조각들이 나열된다. 이런 조각들 사이의 임베딩 유사도는 원래 무의미한 값인데, 이걸 그대로 breakpoint 계산에 넣으면 **표 내부에서 엉뚱하게 여러 번 잘리는 오탐(false positive)** 이 발생한다.

- 감지: PARSE 단계 출력에 표/코드블록 마커가 이미 있으면 그대로 활용하고, 없으면 반복되는 구분자 패턴(파이프 `|`, 코드 펜스 등)으로 휴리스틱 감지한다.
- 처리: 감지된 구간은 **원자 단위(atomic block)**로 취급 — 내부는 유사도 계산 없이 통째로 유지하고, 그 구간의 앞과 뒤 경계만 자동으로 청크 경계로 삼는다(구조가 이미 주제 경계를 의미하기 때문).

### 5.5 문서가 매우 짧을 때 — percentile의 통계적 한계

percentile(백분위수) 기반 임계치는 "이 문서 안에서 상대적으로 유사도가 낮은 지점"을 찾는 방식이라, 표본(인접 문장 쌍 유사도)이 충분히 있어야 의미가 있다. 문장이 5~10개 미만이면 하위 5%를 계산하는 것 자체가 통계적으로 불안정하다(예: 문장 4개면 유사도 쌍이 3개뿐이라 "하위 5%"라는 개념이 사실상 성립하지 않음).

- 대응: 문장 수가 임계값(예: 10개) 미만이면 percentile 계산을 건너뛰고, 전체를 하나의 청크로 처리(단, `max-chars` 상한은 그대로 적용).

### 5.6 기존 색인 문서 — 재색인 시 고려할 것

알고리즘을 바꿔도 이미 Qdrant·PostgreSQL에 저장된 기존 청크는 자동으로 갱신되지 않는다. 재색인이 필요한데, 다음을 함께 고려해야 한다.

- **재색인 범위**: 전체 문서를 한 번에 돌릴지, 카테고리·문서 단위로 점진 적용할지 — 비용(임베딩 API 재호출)과 운영 부담을 감안해 점진 적용을 우선 검토.
- **chunk_id 변경의 파급**: 청킹 알고리즘이 바뀌면 청크 경계·개수 자체가 달라져 `chunk_id`가 새로 생성된다. 과거 `rag_qa_citation`에 남아있는 `chunk_id` 참조는 그 시점의 스냅샷이므로 끊어져도 무방하지만(과거 답변 재현용이 아니라 이력 기록), Graph RAG가 함께 도입된 상태라면 `rag_entity_chunk` 브리지도 재색인 대상 문서에 한해 재추출이 필요하다.
- **기존 설정 재사용**: `reindex-policy: OVERWRITE` 정책을 그대로 활용할 수 있는지 확인.

### 5.7 효과 측정 — 골든셋만으로 충분한가

기존 골든셋(`docs/goldenset.json`)은 Graph RAG 평가용으로 설계되어 `citation_ok`·`answer_ok`·`graph_win`·`no_regression` 기준을 쓴다. 의미 청킹 A/B 비교에도 그대로 재사용할 수 있지만, **청크 경계 자체의 품질**을 직접 재는 지표는 없다는 한계가 있다.

- 골든셋 지표(citation_ok, answer_ok)는 "결과적으로 답이 맞았는지"를 재는 간접 지표다.
- 보조로 청크 품질 자체를 보는 지표를 추가하는 게 좋다 — 예: 청크가 문장 중간에서 끊긴 비율(0에 가까울수록 좋음), 청크 길이의 표준편차(의미 청킹은 들쭉날쭉한 게 정상이므로 편차 자체보다는 "너무 잦은 강제 슬라이스 발생 비율"을 추적).

## 6. 진행 순서

| 단계 | 내용 | 기대 효과 |
|---|---|---|
| 0 | 현재(고정 길이) 청킹 기준 골든셋 baseline 측정 | 개선 여부를 숫자로 비교할 기준선 확보 |
| 1 | PCC에 의미 청킹 프로토타입 추가(feature flag로 기존 방식과 공존) | 운영 중단 없이 신규 알고리즘 검증 |
| 2 | 동일 문서 세트를 두 방식으로 재색인 후 골든셋 재평가 | citation 품질·recall 개선 여부 정량 확인 |
| 3 | percentile 임계치·문장 묶음 단위 튜닝 | 문서 유형별 최적값 도출 |
| 4 | 기본값 전환 + 기존 문서 일괄 재색인 | 전면 적용 |

> 0단계를 먼저 두는 이유: 그래프 RAG 설계와 마찬가지로, 기준 없이는 "의미 청킹이 실제로 더 나은지"를 증명할 수 없다.

## 부록: 개발 세부 (미정 사항)

- rag-storage-service 측 변경: **없음** — `RagChunkWriter`, `PccChunkHints`, `PccIngestResponse` 계약 유지. 재색인 트리거 정도만 필요 시 추가.
- 변경 범위는 전적으로 `langchain-service` 내부(문장 분리기, 경량 임베딩 모델 선정, percentile 계산 로직).
- 미정: 경량 임베딩 모델 선정(로컬 모델 vs 별도 API), percentile 초기값, 문장 묶음(buffer) 단위, feature flag 이름/전환 시점.
- Graph RAG의 PC/C 스테이지 분리(Pass1을 위한 `RagPccWorker` 분리 작업)가 먼저 들어오면, 의미 청킹은 그 분리된 C(청킹) 호출 내부에서 적용하면 된다 — 순서에 의존성은 없으나 같은 파일(PCC 내부 청킹 로직)을 건드리므로 작업 순서를 조율할 것.
